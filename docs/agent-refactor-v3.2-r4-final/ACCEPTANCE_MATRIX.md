## 测试夹具约定

Fake text/image provider 必须可脚本化地产生 accepted、延迟、逐项成功、明确失败、unknown、取消确认与迟到成功；每次调用写入参数规范化 hash 和 provider call ID。持久层使用测试临时目录中的真实 host store，重启用例须销毁进程/实例后重新打开该 store；不能用同一内存对象冒充重启恢复。fake artifact store 提供稳定字节、hash 与附件元数据。

`expectedCount` 是本验收矩阵的夹具简写，必须逐例映射并断言 `get_execution.expectedOutputCount`；它不是另一个产品字段。所有计数以实际边界为准。多图场景分别记录：`execution.enqueue`（持久队列中新建 execution 数）、`image.provider.request`（越过 provider 边界的请求数，不等于图数）、`provider.output.item`（provider 实际返回的逐图结果记录数）、`execution.output.slot`（持久化的输出槽位数，始终等于该 execution 的 `get_execution.expectedOutputCount`，每个 `outputIndex` 恰有一个槽位，包含 `not_dispatched`、`unknown` 等状态），必要时另记成功登记的 artifact 数。未派发槽位不是 provider 返回项；收到 provider 返回的 error/unknown 结果记录仍计入 `provider.output.item`。fake provider 必须分别运行逐图请求和远端 batch 两种模式；batch 的一次请求可以包含多个 outputIndex，已发送的 batch 不能被本地失败护栏追溯改称“未派发”。其他边界仍记录 image.cancel、image.query、paidText.call、file.write、queue.claim、durable.commit。界面文案不作为权威证据；通过条件须同时核对 provider 计数与持久 execution/receipt/event、输入 hash、附件归属或设置 revision。每条测试开始时记录 store snapshot/hash，完成后比较预期差异。

T08–T13 每一行都须对五类公开图片入口分别执行并分别记录结果：`generate_image`、`redraw_image`、`inpaint_image`、`upscale_image`、`process_image`。生图验证 `prepare_generation → generate_image`；四个专用编辑工具验证各自真实 handler 内部的 `prepareExecution` 路径，不额外伪造一次模型公开 prepare 调用。每类入口都要经过实际 host、批准/持久化与 fake provider 边界，并验证 host 注入的 ExecutionSubmissionContext 绑定；不接受模型参数自证授权。一种工具通过不能替另一种工具背书。

层级缩写：SC=工具目录/schema；PI=Pi 消息与原生 call/result；H=IPC host/adapter/权限；D=持久存储；Q=后台队列/worker；UI=渲染器与交互；E2E=以上完整链路。目标协议如未实现，对应行保持 pending，不能改为模拟 handler 自证通过。

本轮目标 registry 经用户确认由原 33 项增至 36 项：新增 `read_creation`、`read_proposal`、`patch_creation_inputs`。前两个是新增只读工具设计，不是现有产品工具；后一个是待实现的输入写入工具。此数量是目标协议范围，不表示固定 HEAD 已实现。

- 当前所有 T01–T29/U01–U07 行及附属 UI 子场景均为 pending。不得写“测试通过”，直到对应五工具 fake-provider host 测试实际运行，并附 run ID、测试版本、provider counter dump 与持久化记录证据。
