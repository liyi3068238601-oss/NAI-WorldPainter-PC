# 绘世 PC Agent v3.2 R3：收尾复审与接线验收建议

日期：2026-10-16。审查对象：`绘世PC_Agent重构设计_v3.2_R3.zip`。

## 结论

**R3 已接近设计收敛。建议保留当前架构、界面和预设机制，完成下列少量收尾后，转入真实 host + fake provider 的最小链路实现。无需再整体重画界面或重写一套设计。**

上一轮的工具发现、前置错误回执、反推正文、共享提交上下文、派生输入、旧预览失效、同图多用途查看器、预设迁移文档等，均有实质修订。不能继续照搬上一轮缺陷清单，称它们仍然没有设计。

剩余问题主要是：**新旧说明未完全同步、聚合校验漏掉部分终态、验收用例未跟上协议，以及新增原型演示的一条残留暂停状态。** 这些适合集中修补，不需要新一轮架构扩张。

这仍是设计审查，不是“工具已经正常运行”的认证。

## 3. 工具合同：三处集中修订

### 3.1 清掉会误导实现者的旧规则

#### A. get_capabilities 的文字摘要仍是旧版本

位置：`TOOL_CONTRACTS.md:47,50,54`。

- 第 47 行仍写 conditional；同文第 12/45 行和实际 registry 已写始终挂载。
- 第 50/54 行仍列旧十组，包括已经不在新目录中的 references，漏掉 image_edit、creation_context、vision_service 等实际组。

**修法：从 registry 生成逐工具摘要，避免手工维护两份目录。** 保留“单次 requestedGroups 最多 10 项”的请求上限，它不等于“总目录只有 10 组”；不要误把这个上限当成错误一起删掉。

#### B. frozenInputRevision 的顶层文字仍指向发送时版本

位置：`tool-registry.json:45`；对照新映射 `:13425–13428`、`TOOLS_AND_FLOWS.md:80–82`。

新的派生机制已经成立，但顶层 executionInputVersion 仍说从 submitted message context 注入，后续不能改变，容易被照抄为“prepare 永远使用最初发送版本”。

统一成三阶段：
1. OriginalMessageSnapshot 不改写。
2. 只有同回合已授权成功 CAS patch 可以派生 TurnEffectiveInputSnapshot。
3. prepare/批准/入队再绑定不可变的 execution 输入。

这里是**旧说明未清理**，不是新派生方案不存在。

#### C. 一个同类摘要漏项

`TOOL_CONTRACTS.md:737` 的 patch 入参摘要漏 referencePurpose，但正文示例及 registry 已有。与 A/B 一起生成修正即可，不需要另起架构任务。

### 3.2 聚合校验还漏掉 error / blocked / denied 分支

位置：`validate_registry.py:77–145`，尤其 `:100–138`；对照 `tool-registry.json` 的 `semanticContracts.executionAggregate` 及 `TOOL_CONTRACTS.md:20`。

新增三个数据反例：
- executionStatus=error；
- executionStatus=blocked；
- executionStatus=denied；

它们都同时带着一个 status=pending 的输出和 providerReceiptStatus=pending。这三份对象可以通过目前 JSON Schema；静态查看附带语义函数，unknown 全局优先级会检查，但 error/blocked/denied 没有对应分支，也没有统一的“在途优先”检查，因此这类对象不会在这些分支被拒绝。

这与合同“有正常在途项应保持 running/cancel_requested，不得提前宣称整体结束”不一致。实际产品尚未实现，不能将其描述为生产端已经误报失败。

**修法：**
- 聚合函数做穷尽状态匹配，不能默默放过合法枚举中的未处理项。
- 将 unknown 优先、正常在途优先做成共享前置规则。
- 对 error/blocked/denied 定义终态证据；仍有 pending/provider pending 时不能把它们当整个 execution 的最终状态。
- “后续派发被阻止”与“当前 execution 已整体终止”分字段，不用同一个 blocked 混写。
- 增加这三例的语义拒绝测试，以及对应的真实合法终态正例。dispatching 等其余枚举也在状态覆盖表中明确，避免遗漏后默认通过。

本次附带 `R3_新增聚合状态反例.json` 保存完整对象。schemaAccepted=true 表示**当前静态结果**；expectedByWrittenContract=false 表示按现有文字合同应拒绝，不是要求修订后仍接受。

### 3.3 U05 的批准/入队时间线与预览失效规则矛盾

- `TOOLS_AND_FLOWS.md:116`：入队事务再次核对修订与 fingerprint，期间变化拒绝旧预览。
- `SYSTEM_PROMPT.md:20,70`：未提交预览变化即失效，已入队不受影响。
- `ACCEPTANCE_MATRIX.md:62` U05 却写 approve 后修改 UI seed，再提交旧 snapshot，并要求 submit=1。

要明确 approve 与 durable enqueue 的边界，不让实现者凭经验二选一。

按当前流程建议把 U05 拆开：
1. **入队前**改变本次预览依赖的 seed：旧提交拒绝，provider request=0；重新预览批准后才提交。
2. **入队后**改变 UI seed：旧 execution hash 不变，provider 仍使用原批准 seed。

若产品把批准和入队做成同一个原子动作，第二项就直接写“入队成功后再修改 UI”，不要保留先修改再提交的歧义。无关创作的 UI 修改不应使另一创作的预览无故失效。

## 4. 验收规格：补两项即可，不必扩大整套目录

### 4.1 给 T28 加真正的“同回合改输入后生成”链路

当前 T28 只测 patch、重放、撤销，并要求 image.submit=0；T23 也不是同回合的派生链路。系统提示词里有行为案例，但不能代替 host 持久证据。

增加 T28 子场景或单独编号：
- “移除改图源，然后生成”。
- “把参考改为仅讨论，然后生成”。
- patch 期间 UI 并发修改；只读刷新不能把无关修改当新授权。

断言：original message hash 不变；patch 回执链及 before/after revision 连续；prepare 的 effectiveSnapshotRef 指向合法派生；provider payload 不含已清源/仅讨论参考；旧 execution hash 不变；成功只有一次入队/派发，冲突没有收费调用。

### 4.2 T08–T13 明确参数化五类图片工具

共用 ExecutionSubmissionContext 已补，但不能只在 generate_image 的 preparation 路径测试后，就宣布全部编辑工具通过。

明确逐一覆盖 generate/redraw/inpaint/upscale/process：双击、accepted 丢失、同键重放、同键不同输入、入队写失败、重启、取消竞争。专用编辑走内部 prepareExecution，不要求模型再发一个公开 prepare 调用。

T29“生成第二张 → 重启 → 编辑 → 放大”的组合验收值得保留。T15 的 output.item 若只计 provider 返回结果，应与 durable output slot 数区分命名，避免把“三张中第三张未派发”误实现为只保存两个状态槽位。

## 5. 原型收尾：一条新卡死路径、一条异步交互残留

### 5.1 取消重启演示任务后，残留全局暂停锁

位置：HTML `3007–3010, 2771–2780, 2550–2552`；继续入口 `1292–1297,1329–1343`。

源码可达路径：
1. 菜单选择“准备恢复场景：未发送排队”。
2. 尚未模拟重启，直接取消这条任务。
3. 对正常提案打开预览并确认生成。

第一步把 demoQueueHold=true；取消只移除任务，没有解除 hold。后续正常任务会进入 queued，但 processGenerationQueue 因 hold 直接返回；普通 queued 卡只有取消，没有恢复入口。等待不会开始，用户只能依赖刷新或其他演示动作改变状态。

**修法：让演示暂停绑定具体持有者。** 取消最后一个持有暂停原因的演示任务后释放这个原因并调度队列；不要无条件清全部暂停，避免另一个演示任务或真正的 failure/unknown gate 被绕过。

回归三条：
- 准备 1 项 → 取消 → 普通生成只提交一次。
- 准备 2 项 → 取消其中一项 → 另一演示项继续未发送。
- 全部演示项取消 → 不再残留无解释的全局 hold；失败/unknown 等独立护栏仍有效。

这是本地原型演示问题，不是已经发生的远端收费问题。

### 5.2 聊天用途回执到达时，仍会重建右栏、折叠并丢焦点

位置：HTML `3439–3441,3342–3345,1212–1218,1837–1839,1942–1947`。

直接在 select 修改用途的旧问题已修。但用户发“把参考图‘橱窗暖光参考’改为仅讨论”后，等待回复时展开右栏并聚焦用途 select，回复完成仍会执行全局 render → renderCreationPanel → replaceChildren。新 details 默认收起，旧 select 被移除。异步图像结果到达也存在同类重绘路径。

**修法：**异步回执只更新时间线和实际变化的控件，或按稳定 sectionId/bindingId 恢复展开、滚动和焦点。仅在原焦点确实处于被替换区域时恢复，不把用户焦点从正在输入的 composer 强拉走。

补测“回复等待期间操作右栏”“图像结果到达时操作参考区”；不要只测同步 onchange。

### 5.3 可随手补的键盘细节

HTML `3792–3800` 翻页后尝试恢复到原 previous/next；到首尾时该按钮已 disabled（`3721,3724`），焦点恢复失败。选择一个有效落点，例如仍可用的导航按钮、范围控件或当前图标题。范围 select 本身的旧焦点问题已修，不需要重复报告。

## 6. 预设、界面和范围的判断

- **保留现有预设设计。** R3 已把助手预设与图片提示词预设、模板、批准模式分开；会话选择、新会话默认、共享编辑、已发送回合快照均有明确边界。
- PRESET_COMPATIBILITY 已随包交付，覆盖 normalize 前原始归档、未知高版本只读、自定义正文/未知字段保留、引用修复和失败回滚。接下来要用真实主进程迁移测试证明，不需要再换预设体系。
- 主界面视觉可冻结。摘要方案卡、大图、紧凑输入、右栏和窄窗入口已足够稳定，优先修异步状态与焦点，不再为本轮重新选配色或重排三栏。
- 本地 sessionStorage 恢复、可选模拟回执、示例 SVG 下载都明确标注为演示，不能升级成磁盘崩溃恢复、远端取消或原图下载通过。作者已披露这些边界，不把它们再当“隐瞒的新缺陷”。

## 7. 可直接交给 Agent 的收尾任务

> 以 v3.2 R3 为冻结候选，不重做 UI 或 Agent 框架，保留预设机制。先完成这组集中修订：
>
> 1. 从 registry 同步生成 get_capabilities 的文字摘要；删除旧 conditional/旧十组说明，保留单次请求上限。同步 frozenInputRevision 顶层三阶段说明及 patch referencePurpose 摘要。
> 2. 将执行聚合校验改成穷尽状态处理，补 error/blocked/denied + pending 的拒绝测试，以及合法终态正例。后续派发被阻止不能冒充在途任务整体结束。
> 3. 统一 U05 与预览失效政策：明确入队前变化拒绝、入队后旧快照不改。增加同回合 patch→prepare→submit 的持久证据断言；把 T08–T13 明确参数化五类图片工具。
> 4. 修演示 demoQueueHold 的持有者与释放条件，覆盖单项/多项取消后的普通生成；不得解除独立 failure/unknown gate。
> 5. 修异步聊天/图片回执导致右栏折叠和焦点丢失；补 viewer 首尾 disabled 导航的焦点落点。
> 6. 更新关闭表、样例和验证记录，只标记实际执行过的层级。设计与原型收尾完成后，转入最小 host + fake provider 链路，不再只靠增加设计文档证明运行可靠。
>
> 最小实现闭环建议：读取创作 → 提案 → prepare → 批准并持久入队 → worker → 成功产物登记 → get_execution → 用第二张派生编辑。同步验证取消、unknown、重启、旧历史投影及预设迁移保护。之后再扩到全部工具。
>
> 交付必须区分静态 schema、原型交互、host 集成、真实模型/服务四层证据。真实收费服务仅在明确账号与预算授权后验证，不用固定演示计数替代 provider 请求计数。

**总体建议：修完上述收尾就应开始小步实现和故障注入，而不是再进行大规模设计改版。**
