# 绘世 PC v3.2：工具调用设计审查与验收要求

审查日期：2026-10-16。对象：用户上传的 v3.2 设计包与当前 Electron 源码。目的：把“可理解的交互方案”推进为能够可靠实现、可验证的工具协议。

## 结论与证据边界

**界面设计可以收敛，工具协议仍需补齐后才能按可靠实现进入验收。当前不能宣布“工具已能正常运行”。**

33 个目标工具名称唯一，29 个旧入口加 4 个新增入口的数量闭合；直接方案生成、独立工作台、accepted 与图像终态分离、原生 call/result 一对一的方向正确。问题主要在协议细节和从当前同步运行时迁移到异步执行的边界，不需要再换框架或推倒 UI。

本次通过 GitHub connector 重新确认 `feat/electron-m4-migration` HEAD 仍是 `dfd7caa63ae19bd40651e00127a71efe57b71b4e`。进行了源码和设计静态核对，未启动产品、未运行真实模型或生图服务、未验证扣费/远端取消，也未修改产品代码。

下文“阻断”指**发布可靠运行结论之前必须解决**，不表示这些新设计已在生产发生故障。文件行号对应本次 v3.2 包；后续修改可能移动。

## 一、必须先闭合的工具协议

### 1. 33 个名称不等于 33 份可执行契约

TOOLS_AND_FLOWS 的目录大量使用“当前 schema 支持”“现有字段”“例如”等描述，JSON 示例是调用样例，不是 JSON Schema。尚不能据此统一模型参数生成、host 校验、确认卡和旧 handler。

必须交付唯一、机器可读的工具登记表，逐项含：

- canonical 名、schemaVersion、旧 handler 及字段转换。
- inputSchema 与 resultSchema：必填、类型、枚举、范围、默认值、未知字段策略。
- availability、effect、approval、可能费用与能力要求。
- 统一错误码和错误后的允许动作。

重点约束：prepare_generation 的“提案引用/直接提示词”二选一；propose_prompt 的 proposalId/baseRevision 成对；process_image 按操作分支限制字段；只允许服务真实支持的 scale/model/reference 组合。不要在模型可见 schema 中省略限制，最后靠模糊报错补救。

不同供应商可能支持不同 JSON Schema 子集。可以投影更简洁的模型 schema，但 host 必须执行完整验证；不兼容结构应在接入测试中暴露。

### 2. CAS 参数要有可靠的获取和刷新入口

set_current_proposal 要求 expectedSelectionRevision；apply_prompt 要求 targetDraftId/expectedDraftRevision；修订提案还需要旧版正文与 baseRevision。

当前设计虽然要求 host 注入部分状态，却没有闭合“缺状态或冲突后如何刷新”。read_generation_state 只描述了模型、尺寸等生成参数，没有明确返回工作台版本。不能让模型猜 revision，也不能要求用户提供内部 ID。

最小修订有两条可选路线，不强制维持工具总数：

1. 扩展 read_generation_state 返回 draftId、draftRevision 和来源；由 host 在明确安全节点提供可请求刷新的 CreationContext，包括目标创作、指针修订和被引用提案正文。
2. 增加窄职责的 read_creation/read_proposal；同步修订工具总数与挂载规则。

冲突回执返回当前真实状态和版本。**刷新不代表允许自动覆盖**：用户先前确认的输入和工作台目标变动后，必要时重新展示差异或预览。旧卡操作刷新旧卡所属创作，而不是当前前台创作。

### 3. 生成产物必须能直接成为下一次工具输入

设计的异步事件与 outputs 主要返回 artifactId，但 redraw/inpaint/upscale/reverse/read_image_metadata 接受 attachmentId，二者的映射尚未正式规定。

统一使用一种稳定 ID，或让成功 output 至少返回 artifactId、attachmentId、attachmentRevision/hash、outputIndex、conversationId、creationId、parentAttachmentId。产物登记与成功回执须可靠提交，公开可用结果之前确认附件能读取。

验收必须贯通“生成两张 → 选择第二张 → 直接重绘/放大 → 重启后继续读取”。仅有图片 URL、界面缩略图或某个当前选中项不够。

### 4. 工具调用完成与业务成功必须分别判定

外层 completed 表示命令已经处理，不应让所有卡片和模型都把它解释为“目标动作成功”。明确各工具 data 的判别字段：

- propose_prompt：proposalStatus 与有效版本。
- set_current_proposal：selectionStatus=applied/unchanged/conflict/not_found/invalid。
- apply_prompt：applyStatus 与真实工作台修订；conflict 不显示已应用。
- generate/编辑提交：accepted 必须带 executionId 和执行阶段。
- get_execution：外层查询完成，内层可能仍 running/unknown。
- cancel_execution：cancelDisposition 区分 requested/already_terminal/not_cancellable/not_found，并保留实际终态。

取消一个已完成任务应返回“已完成，未取消”，保留作品；不能把 completed 降成 cancelled，也不能因枚举遗漏而报成未知。

模型自然语言、工具组图标、任务卡和作品卡必须读取同一规范化结果，不各自猜成功。

## 二、从当前源码迁移时，不能直接复用的假设

### 5. 平铺参数要改完整链路，历史投影与新执行校验分开

当前 Pi 工具 schema、execute、beforeToolCall、事件解析以及历史构造均使用 `{args:{...}}`。只换模型工具描述，授权层或执行层仍会读错。

同步修改并测试：schema → 校验 → 授权预览 → handler adapter → 事件 → 结果归一化 → 历史投影。

旧调用还缺少 creationId、proposalId、工作台 CAS 等新字段，不能为了让历史通过新 schema 而填当前创作或伪造提案。旧生图通常是同步终态/产物，新生图是 accepted；旧结果状态也不一定符合新枚举。

要求保存原始历史和 protocol/schemaVersion；仅模型上下文投影做版本适配。不能执行 handler 来“补历史”。无法配对或无法准确迁移的旧记录，保留为明确的惰性历史说明，不伪造成功。原生历史必须保持每个 call 的唯一 result；未知工具和正文里的工具名不做全文替换。

### 6. 当前单回合付费保护不会自动覆盖后台任务

源码里的 paidFailed 在等待 execute 返回失败或抛错时生效。改成 execute 很快返回 accepted 后，数秒后的图像失败不会自动设置这个回合闭包的失败状态。

而 paidActions 以工具名与原始 args 去重；当前 Pi generate schema 的唯一入参是 preparationId，换一个 preparationId 就是不同键。这不是持久化业务幂等。

因此 turn/batch 的失败停止标记必须由 host 持久维护，图像 dispatch 与相关收费文字工具执行前都重新检查。逐张 output 的 error/unknown 也要触发，不等整批 aggregate 变失败才停。失败回执与停止标记应先持久提交，再唤醒下一个任务。

已有同回合保护继续保留，但只能作为第一层保护，不能代替后台调度检查。

### 7. 停止对话不等于取消指定图像任务

当前 abortAgentMessage 中止的是会话控制器。生成/重绘/编辑 handler 的 signal 传递并不统一；不能直接把它更名为 cancel_execution。全局 cancelAllJobs 也不能代替单个 execution 的取消，否则可能停止别的创作任务。

建立 executionId 对应的本地执行控制、服务任务 ID 与可取消能力。尚未提交可确定取消；已经发送则只能按服务支持请求取消。服务不支持时如实返回“不支持远端取消/结果待核实”，不要把中止等待当成远端停止或退款。

### 字段级适配清单：不能仅按名称透传

以下均由当前源码核对，需在工具登记表中逐项决策：

| 项目 | 当前差异 | 修订要求 |
| --- | --- | --- |
| 图库来源/筛选 | Pi schema 的部分来源不被 handler 接受，会回退 danbooru；safeOnly 在 handler 支持但 schema 未暴露 | 对不支持来源明确拒绝或实现；不静默换站；保留明确安全筛选 |
| 画师/参考预设查询 | scope、group、limit 等部分字段 handler 有而 Pi schema 没有 | 对齐输入与实际执行；不能宣称字段已生效 |
| 图片提示词预设 | negative 类别在旧 handler 会退回 all；保存只追加正面预设，缺类别/revision | 不把 schema 上存在当实现支持；补能力或显式限制 |
| 模板版本 | 旧 templateVersion 实际表示 v5/v4.5，并非模板正文修订号 | 分开模型/提示词版本与 templateRevision；不能共用一个字段 |
| 编辑提示词 | 原字段 currentPrompt/instruction/kind/mode/templateVersion | 新字段明确映射；不能丢用户 instruction 或 mode |
| 记忆候选 | 旧 handler 为 type 和 scope，不是 category | 明确 category→type，保留 global/conversation 范围 |
| 局部重绘 | 使用 inpaintModel，且部分高级参考不支持 | 与普通 model 分开映射，不删掉不支持字段后偷偷退化 |
| 原生生图 | 种子策略、CFG、采样器、质量、Vibe、精准参考、多角色等已有参数 | 逐项保留；不要只保留 prompt/model/size/count 导致重构减功能 |
| 兼容图片服务 | 底层仅接受 positivePrompt/count/model 等限定参数，且只支持文生图 | adapter 先消化 conversation/creation/proposal 等领域字段；不透传给底层，不挂出不可用编辑工具 |

当前授权逻辑对非 readonly 工具统一走 authorize。新设计的 propose_prompt/set_current_proposal/cancel_execution 是写入但 approval=none，必须让 host 真正读取独立 approval 策略；不能为了免确认把它们伪标为只读。paid 分类同样要统一覆盖收费文字、视觉与图像服务。

当前准备机制冻结原始 args 和配置 fingerprint，但 handler 执行时仍读取设置、附件并应用锁定词。新执行快照要保存**实际生效输入**；dispatch 的重新校验只判断是否仍可执行，不能用最新默认值重算已批准内容。

## 三、异步执行必须补上的原子边界

### 8. 准备令牌消费、任务入队、提交回执要原子提交

分别写“只消费一次”和“持久队列”仍不足：先消费后崩溃会丢任务，先入队后崩溃可能再次入队。accepted 响应丢失后，用户还必须能找回原 execution。

最小契约：校验授权指纹 → 消费 preparation → 保存 snapshot/execution/初始 receipt → 保存 submissionKey 映射，组成一次可靠提交。提交成功后 worker 才能领取，才可返回 accepted。

submissionKey 对应稳定的提交意图，传输重试不能重新生成一个新键。相同合法重放返回原 execution 与回执；同键不同参数拒绝。改图没有 preparation，也需要等价的幂等入队规则。

不强制使用某种数据库，但所选文件/日志/事务方案必须通过断电和写入失败测试。

### 9. 取消与 dispatch 争用同一个状态转换

不能“先读 queued，再各自执行”：取消方和 worker 都可能读到 queued，随后一方显示 cancelled、另一方已经发出了收费请求。

必须通过原子竞争决定谁取得执行权：

- worker 仅能以 queued→dispatching 的 CAS/事务领取，并在领取时检查取消意图、停止标记和全局暂停。
- 排队取消若赢得 queued→cancelled，保证远端发送次数为零。
- 取消若输给 dispatching，登记 cancel_requested；没有证据不能写 cancelled。
- 服务 ID 尚未返回时保留取消意图，待可定位任务后再请求取消。迟到成功仍保存产物。

### 10. 重启恢复区分“尚未首次发送”和“可能已经发送”

建议恢复表：

| 持久证据 | 恢复方式 |
| --- | --- |
| durable queued，确定无发送尝试 | 保留为待执行；是否自动继续按既定启动策略明确规定，首次发送前再校验授权与失效状态 |
| dispatching/running/cancel_requested，缺终态 | 先核实，不能自动重发；没有查询能力则保持 unknown |
| completed/partial 且有输出 | 恢复作品与状态，不重做成功步骤 |
| turn/batch 已停止或 unknown gate 存在 | 先恢复阻塞，再启动 worker，不能反过来 |

本地幂等不能单独保证远端 exactly-once。远端不支持幂等键/查询时，请求已发但结果丢失必须承认不确定，而非猜测没执行。

## 四、消息排队和引导不能破坏原生工具协议

### 11. 修正“截止发送序号”与“补齐前轮回执”的冲突

TOOLS_AND_FLOWS 第103行按排队消息的发送边界截断上下文，但 SYSTEM_PROMPT 又要求补齐前轮完成回执。

具体时序：A 发工具调用 → 用户发送排队消息 B → A 工具结果返回 → A 结束 → B 开始。如果按 B 的发送时刻截断，A 的结果必然丢失，甚至留下孤立 toolCall。

改为两个独立顺序：用户提交顺序控制排队；模型上下文按因果依赖组装。B 开始时纳入前驱 A 完整的消息和 call/result 闭包，再处理 B；晚提交的用户消息 C 不倒灌。B 的原文、显式版本、附件和预设仍按发送时冻结，不与因果历史混为一个快照。

### 12. 引导只改变处理归属，不能先删除消息

引导从待发队列移出，到模型在安全节点接收之间，如果停止或崩溃，可能丢失；如果正常结束与接收同时发生，可能既引导一次又独立回答一次。

消息应持久保留，通过 messageId 与状态版本实现唯一归属：pending → steering_pending → consumed_by_turn，或退回 fallback_queued。接收与写入因果输入事件必须可靠提交；停止后的未消费消息保持暂停，不自动接着运行。

取消、终轮和重启都不能重放已经提交的工具。正在等待确认的 call 被停止时，应撤销过期确认入口并保存真实未执行结果；已提交的图像 call 回填原 accepted；已经发出的收费同步请求按实际结果或 unknown 闭合。不能丢掉 call，也不能给同一 call 发第二份矛盾结果。

## 五、其他必须写清但不必扩大框架的规则

1. **工具发现**：按需挂载需要可恢复路径。第一步检索后需要生成时，host 如何补挂下一步工具必须明确；不能只返回当前挂载列表而无能力扩展路径。联网关闭等限制不因发现而解除。
2. **作用域**：list_history 的输入/host 注入目标要明确；不能读 UI 当前前台会话代替冻结目标。模型提供的 ID 只是待验证引用，host 仍负责归属检查。
3. **设置指针幂等**：成功响应丢失后，同 call 重放先返回原回执，不再因 revision 已变报冲突；同键不同参数拒绝；unchanged 不制造新撤销按钮。
4. **点评**：按 batch 唯一调度，进入同一会话串行器，不能另开并发模型回合。只把实际送达的像素算看图；重复事件/迟到结果不触发重复自动点评。
5. **界面输入与工具快照**：v3.2 中“删除源图胶囊未清改图绑定”“仅讨论仍可参与生成”的两个问题，要在 host 同样设不变量，不能只靠 UI 禁用选项。

| T19 | 引导接收与回合结束/停止竞争 | 每个 messageId 仅处理一次；未消费内容仍可恢复 |

| T21 | 29 旧工具历史、新旧结果、残缺/重复记录 | 不执行 handler；原始记录不改；投影满足供应商协议 |
| T22 | 切换前台后读取历史/取消任务 | 严格使用明确来源范围，不误读或取消别处 |
| T23 | 删除改图源、仅讨论参考、无蒙版重绘 | 真正清除源；仅讨论不发送；缺蒙版时不静默降级 |
| T24 | 重复完成事件/点评期间用户发消息 | 同批最多一次自动点评，无并行回合争写 |
| T25 | 图库来源、negative 类别、模板版本、兼容渠道 | 不静默换来源/类别；模板修订与v5/v4.5分开；不支持能力明确拒绝 |
| T26 | confirm 模式下免卡本地工具及收费文字工具 | 写入分类准确；免卡依approval策略；收费提示准确 |
| T27 | 准备后修改全局默认/锁定词/附件 | 不重算已批准快照；失效则阻塞，保留原输入 |

每个假服务记录 submit/cancel/query 次数、输入 hash、执行 ID、产物 ID；断言要检查副作用次数，而不只检查返回文案。

## 七、实施与验证顺序

1. 明确 schema、状态读取、ID 映射、输出合同和 legacy adapter。
2. 修复排队因果上下文规则；定义所有原子状态转换和恢复表。
3. 在真实 host 服务层用 fake provider 打通完整调用链，通过 T01–T27。
4. 再接真实 Pi/模型，验证工具选择、参数生成、历史回放、多个供应商协议差异。记录真实请求与回执，不能用固定原型文本代替。
5. 最后在明确账号、费用与操作范围下验证真实图像服务的提交、返回、超时和取消。没有预算授权不进行付费测试。

验收记录分开报告：静态协议检查、host 自动测试、真实模型协议测试、真实图像服务验证。任何一项未做就标未做；不要以按钮可点击、HTML 无错误或工具名数量正确来宣布端到端通过。
