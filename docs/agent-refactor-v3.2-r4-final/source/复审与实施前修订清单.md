## 4. 工具协议仍需修订的内容

### P1-01：工具发现入口本身有条件挂载，组名又没有完整映射

`get_capabilities` 自身是 `conditional`。它接受的 requestedGroups 只有 generation、prompt、templates、references、gallery、web、memory、skills、questions、execution；其他工具的 availability.group 却包含 creation_context、history、tags、artists、prompt_presets、reference_presets、image_edit、prompt_service、vision_service 等。

当前合同没有一份明确的“请求组 → 实际工具组/工具名”映射。于是模型遇到缺少 read_creation、upscale_image 或 reverse_prompt 时，未必有合法的请求值；发现入口自身未挂载时也缺少保证可达的路径。

修订要求：
1. 把 get_capabilities 设为始终可用的最小发现入口，或明确等价且保证可达的 host 发现协议。
2. 用单一枚举/映射定义请求组、返回组及工具所属组；若使用别名，写成机器可读的映射，不让模型猜。
3. 返回下一安全步骤实际 mounted 的 canonical 名、catalogVersion 与拒绝原因。挂载失败不能继续假装工具存在。
4. 增加“初始只挂最小工具集 → 请求状态读取/编辑/视觉组 → 下一步合法调用”的测试，同时覆盖禁用联网/收费能力。

这解决的是工具能否被真正调用到，不是工具总数是否等于 36。

### P1-02：同一条指令“先改输入，再生成”缺少派生快照规则

`tool-registry.json:45` 把 frozenInputRevision 固定为消息提交时的版本；`TOOL_CONTRACTS.md` 的 prepare 注入也沿用发送时修订。但 `patch_creation_inputs` 可以在同一回合先修改用途/清源并增加修订。

例如用户发“把这张改为仅讨论，然后生成”。patch 成功后，prepare 如果继续取发送时旧修订，就会遇到旧参考回流或 stale；如果直接读任意最新 UI 状态，又破坏已发送消息冻结规则。

修订要求：
- 保留原始 message snapshot 不变。
- 明确建立 **本回合经授权命令派生的 effective input snapshot**。仅允许同一目标、同一用户意图下的成功 patch 回执推进该回合输入基线，并记录 parent snapshot、actionId、before/after revision。
- UI 的无关后续修改、其他回合的 patch、普通只读刷新不能自动推进当前回合快照。
- prepare 使用该派生快照；批准后 execution snapshot 再次冻结。冲突时返回真实差异，不静默套最新状态。

必测：“清源再生成”“改为仅讨论再生成”、patch 期间 UI 并发改动，以及已经提交的旧 execution 不受影响。

### P1-03：所有收费图片工具须引用同一套提交上下文

redraw/inpaint 的 hostInjectedFields 已列出 submissionKey、userIntentRef、frozenInputRevision 等；upscale/process 仍主要列 operationKey、providerBinding、attachmentBinding、approvalReceipt。总流程要求所有图片操作都可靠入队，但逐工具登记表并未完整表达相同保证。

这不证明超分已经会重复收费；它说明按单工具条目实现时容易漏掉共同要求。

建议定义统一 `ExecutionSubmissionContext`，由 generate/redraw/inpaint/upscale/process 明确引用：稳定提交意图与 submissionKey、目标范围、批准回执、有效输入快照、附件版本/hash、provider/account 安全引用、失败 gate 关联。每项工具另外列出自己的参数，不重复手写五份可能漂移的公共字段。对每个图片工具分别测丢 accepted、重放、同 key 不同 payload、重启及取消。

### P1-04：参数错误时，结果 schema 反而要求填写不存在的业务字段

位置：`tool-registry.json:4902–4905, 5015–5019`（get_execution）；`1349–1353, 1386–1391`（search_tags）。

已经用新增反例验证：
- 调用 get_execution 时缺 executionId，host 应诚实返回 invalid_arguments；但结果 schema 仍强制 data.executionId 为非空字符串。
- search_tags 缺 query，错误结果仍要求合法 query、items 和仅有 ok/no_match 的 searchStatus。

于是正常拒绝也可能过不了结果校验。不能靠编 dummy ID、把无效 query 改成别的值、伪装“没有搜索结果”或关闭全部结果验证解决。

**修订：用判别联合区分正常业务结果与前置失败。** 参数校验/权限失败只要求当时已知的上下文、错误码、字段问题和安全恢复动作；业务 ID 在无法获取时不必填。合法输入查询不存在的记录，则仍可返回原 executionId + not_found，这与“输入本来就没有 ID”不同。目标解析失败也不得伪造 conversation/creation。

给每个工具补“非法输入 → handler/provider 零副作用 → 合法失败结果”的测试。不要只测非法输入会被拒绝，还要测拒绝之后能否给模型一个可理解、可校验的工具结果。

### P1-05：反推工具能合法返回“成功但没有文字”

位置：`tool-registry.json:9490–9530`；`TOOL_CONTRACTS.md:523`。

reverse_prompt 的 data 只强制 serviceStatus 与 attachmentId。新增反例实际被现 schema 接受：
- succeeded，没有 candidateText、没有 uncertainty；
- failed，却携带看似可复用的 candidateText；
- 外层 denied，内层 succeeded。

convert/edit 已有较完整的成功正文条件，reverse 不应漏掉。

修订：succeeded 必须有非空正文及明确的不确定性说明；失败/unknown 如保留部分文字，使用独立 partialText/partial 标志，不让它被当作完成结果。规定 denied/cancelled/error 与内部业务状态的合法组合。继续允许 completed+conflict 等真实业务失败，不要把所有 completed 强制等同成功。

### P2-06：状态与种子的一致性尚未由可验证规则封闭

`get_execution` 的返回 schema 允许 fixed+null、random+整数；也允许 executionStatus=completed 但 outputs=[]，或输出只有 failed。

这里需要区分：结构合法不代表业务状态正确。可以用 schema 条件，或用明确的 host 语义验证实现，但必须可测：
- 请求 seedPolicy 与 requestedSeed 复用 prepare 的同一规则；逐图实际 seed 仍只认真实证据。
- 图像任务 completed 必须符合期望数量及成功输出规则，不得包含未结束/失败项。
- partial、unknown、running 的聚合优先级写成状态表，明确“成功图 + 未知项 + 正常在途项”怎么显示。
- 不把此次静态 schema 通过当成聚合函数正确的证明。

位置：`tool-registry.json:4883–4976`；新增反例文件中有完整对象。

### P2-07：验证器中有一段检查实际上执行了零次

`validate_registry.py:48–60` 的 walk_objects 只递归 yield from，从未 yield 对象。因此 `258–267` 依赖它产出对象的附件身份完整性检查，是空循环。

需准确限定：递归过程中的 additionalProperties 断言仍会执行，不能说整个校验器无效；但后面的对象检查确实没有覆盖。

修复也不能只加一行 yield：get_execution 的未完成 output 本来不应强制拥有成功附件，身份字段是在 completed 分支条件必填。应分别验证普通附件及“完成输出”分支，增加 mutation test：主动从完成分支删掉 attachmentRevision/hash 等字段，验证检查器一定报错；未完成输出仍可不含产物身份。

同时建立覆盖表：36 个工具至少各有合法输入、边界/非法输入、正常结果、前置错误结果。63 例全部符合预期是真实进展，但只有 13 个工具有例子，不能代替全目录测试。

### P2-08：Host 注入声明和字段映射需自动校验一致

convert_prompt/edit_prompt 的 hostInjectedFields 只有目标范围，fieldMappings.hostInjected 却要求 operationKey；文档的 Host-only 与 Host 注入两列也不一致。

位置：`tool-registry.json:8688–8691, 8977–8979, 9028–9031, 9324–9327`；`TOOL_CONTRACTS.md:485/491, 505/511`。

将收费文字操作的稳定键声明补齐，或明确由共享上下文继承；验证器应检查每个映射依赖的 host 字段都有声明或确定的派生来源。不要让字段表、代码生成器和实现者得到三个答案。

## 5. 原型中仍可推导出的交互问题

### U1｜高优先：清源后，已打开但未确认的预览仍可提交旧源

位置：HTML `1257–1261, 2075–2106, 2170–2181, 2470, 2486–2489`。

源码可达路径：
1. 选择一张作品为改图源。
2. 发送精确示例短语“移除改图源”。
3. 在约 4.5 秒模拟回复结束前，打开“用此版本生成”的预览。
4. 等待清源完成，胶囊和当前输入已清空。
5. 确认仍然打开的预览。

原因：generationSnapshot 没有 inputRevision；revision 更新不使 modal 失效；确认回调直接 enqueueGeneration(snapshot)。因此未提交的旧快照仍可进入队列。

修订：预览持有 target、inputRevision、fingerprint；相关输入更新后将预览标为失效并禁用确认；重新计算并再次确认。提交阶段再原子核验一次，不能仅靠按钮禁用。**已经入队的任务继续保持旧快照，尚未确认的预览则不能冒充已批准任务。**

截图中的“清源后重新打开预览”证明正常路径，不覆盖这个异步窗口。补测清源前确认、清源后确认、预览期间用途变化、已入队后清源四类路径。

### U2｜中优先：同图兼作作品和参考时，查看器显示错误用途

位置：HTML `1102–1108, 2760–2771, 2887–2890, 3006–3019`。

把作品设为“色彩参考”并允许生成，再从右栏参考缩略图打开查看器：findImage 优先返回 artworks，role/include 却在 references 记录上。查看器于是可能显示“仅讨论，不进入生成快照”，而生成快照实际仍包含该参考。

修订：图片资产与使用绑定分开读取。图像字节来自 asset，当前用途与 include 来自明确 binding；viewer 不得仅凭相同 assetId 猜用途。至少 reference 入口必须读取 findReference。

补测同图分别为色彩+true、色彩+false、仅讨论，以及同图同时为改图源；胶囊、右栏、viewer、预览四处必须一致。

### U3｜中低优先：改用途或参与勾选后，右栏反复折叠并丢焦点

位置：HTML `1667–1669, 1770–1776, 3541–3558`。

change 会整体 replaceChildren，重建的 details 没保存 open。用户展开参考区，把仅讨论改成色彩后，区块关闭；还得再展开才能勾选，勾完又关闭。键盘焦点也随旧节点被删除。

改成局部更新，或显式保留展开、滚动、焦点状态。这比继续调整配色更值得先做。

### U4｜低优先：查看器两个键盘细节

- 范围 select 的 id 是 viewerScopeSelect，但焦点恢复查询的是 data-action，匹配不到。位置 `2819–2821, 2896–2900, 3560–3562`。恢复到实际的新 select。
- 大图容器 role=button/tabindex=0，但 Enter/Space 委托只匹配另一类名。位置 `1075–1081, 3454–3456, 3642–3646`。补键盘行为或用真实按钮；工具栏缩放按钮目前仍可使用，不能因此说整个缩放功能失效。

### 视觉和低频交互建议

当前深色/浅色、窄窗、大图、摘要方案卡可保留。下一轮只做局部调整：
- 右栏“允许进入生成快照”简化为“参与生成”，完整含义留给说明和可访问名称。
- 撤销冲突在回执旁留下固定状态，不只显示几秒 toast。

## 6. 验收矩阵还需修正两类边界

### 6.1 多图测试要区分“一张一次请求”和“一次提交多张”

T15 写第一张成功、第二张失败、第三张未派发，却固定 submit=1；T07 的两张也固定一次 submit。当前这些计数没有解释服务请求粒度。

请拆开两种 fake provider：
- **逐图请求**：第一张成功、第二张已请求失败，通常是两次 provider submit；第三张请求数为零。
- **远端批量请求**：一次 count=3 已经把三张一起提交，不能因为本地 gate 就把第三张宣称为 not_dispatched。应按服务回执判断，不知道就是未知。

分别记录 execution 入队、provider request、output item 三层计数。失败护栏能够阻止“后续尚未派发的请求”，不能撤回已经发出的批量请求。多图取消、幂等、重启也按实际请求边界测试。

### 6.2 自动点评去重入队之后，还要定义消息落库的交付点

现有唯一点评键和同会话串行器已很好地解决重复调度。再明确：点评消息已经保存、delivered 状态尚未保存时崩溃，如何恢复？

消息与最终消费回执应可靠提交；恢复不重跑已交付点评。无像素/模型不支持可记 skipped。若只承诺最多一次并允许崩溃时丢点评，也应明说，不必为了可选点评承诺远端模型调用 exactly-once。给 T24 增加 claim 后崩溃、消息保存边界崩溃、像素不可用的用例。

### 小型文档勘误

- U01/U02 要求 viewer 可切“全部对话”，但 D18/UI_SPEC 只约定“本批次/当前创作全部作品”。统一成已选定范围，不因测试表多写了一个范围就扩大功能。
- MIGRATION_REVIEW 指 viewer 规则在 U06，实际 U06 是下载；范围主要是 U01/U02。
- 把 T07“生成第二张后编辑”与 T13 重启结合，覆盖“生成 → 重启 → 读取第二张 → 编辑/放大”，不能只分开通过。

## 7. 预设设计继续保留，迁移要求必须随实施包交接

你要求保留现有系统提示词“预设”，本版方向仍满足：会话选择、新会话默认、启用状态独立；共享预设更新不回写已发送消息；基础规则与角色/创作预设分层。

但 r2 ZIP 只附本轮材料，旧 `PRESET_COMPATIBILITY.md` 不在包内，主要以“沿用”一句继承。若把 r2 单独交给实现 Agent，容易丢掉既有迁移要求。建议把权威兼容文档复制进最终实施包，或明确提供可访问的固定版本位置和验收项。

## 8. 建议交给实现 Agent 的下一步

以下是可直接复制的任务说明；只授权执行者按你另行指定的工作范围开展，不意味着本次已经修改产品。

> 以 v3.2-r2 为设计基线，保留界面布局和系统提示词预设机制。本轮先闭合合同与原型问题，不换 Agent 框架、不添加泛化工作流工具。
>
> 1. 统一工具发现组名及映射，确保发现入口始终可达；以受限初始目录测试按需补挂。
> 2. 为同回合明确 patch → prepare 定义可追溯的派生输入快照，原消息和已批准 execution 不回写；无关 UI 更新不能自动混入。
> 3. 统一所有图片执行工具的 host submission context，同时对齐收费文字工具的 operationKey 声明。
> 4. 将前置错误 envelope 与正常业务 data 分支拆开；非法输入要能返回合法且诚实的错误结果。补齐 reverse_prompt 成功正文、状态组合、get_execution seed/聚合语义。
> 5. 修复 validator 空循环，并用 mutation tests 证明检查真正能发现缺失字段。补齐全部 36 项工具的基本正反样例，覆盖条件分支而非只凑数量。
